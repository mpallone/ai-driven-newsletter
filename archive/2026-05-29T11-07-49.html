Opus 4.8 lets you update system instructions mid-loop without breaking the prompt cache

  • Source: Anthropic — Claude Opus 4.8 release notes, May 28, 2026; Simon Willison analysis, May 28, 2026
  • Link: Introducing Claude Opus 4.8 — anthropic.com
  • TL;DR: Opus 4.8 now accepts role: "system" entries inside the messages array (immediately after a user turn). You can inject updated permissions, token budgets, or environment state mid-task without rebuilding the full message history — the earlier turns stay cached. Bonus: the minimum prompt length that qualifies for caching dropped from roughly 2,048 tokens to 1,024, so shorter prompts that previously got no cache benefit now do. Older models including Opus 4.7 reject mid-conversation system entries with a 400 error.
  • What to do: Replace any harness logic that restates the full system prompt to update mid-task instructions with a short appended {"role": "system", "content": "..."} entry; on long-running agentic tasks this keeps cache hits on all preceding turns and can drop effective input cost to ~5% of standard on cached batches.
  • Why trust it: Documented in Anthropic's official Opus 4.8 release notes; these are deterministic API behavior changes, not benchmark claims. Simon Willison independently highlighted the same feature in his May 28 post.
  • Skeptic check: Mid-conversation system placement rules aren't fully documented yet; test your specific message structure before deploying, since malformed placement still returns a 400.

Opus 4.8 defaults effort to "high" and only triggers reasoning when it judges it's needed

  • Source: Anthropic — Claude Opus 4.8 API docs and release notes, May 28, 2026
  • Link: What's new in Claude Opus 4.8 — platform.claude.com
  • TL;DR: Opus 4.8 ships with a new effort parameter (values: low, high, max; default: high on all surfaces). Adaptive thinking is on at the high level: Claude only invokes its extended reasoning mode when it judges the current turn needs it, skipping it on simple lookups and short agentic steps. On Opus 4.7 at the same effort level, reasoning fired more broadly and wasted tokens on bimodal workloads. Setting effort: low trades some quality for speed and cost; max forces maximum reasoning every turn.
  • What to do: Start with the default (effort: high) and monitor where you're spending thinking tokens; drop to effort: low for cheap routing or classification steps in multi-step pipelines, and reserve max for genuinely hard planning turns where you want full reasoning every time.
  • Why trust it: Documented in Anthropic's official API docs as a defined API parameter with stated default; behavioral description of adaptive thinking reflects Anthropic's stated design intent, not an independent benchmark. Fast mode at 2× standard price / 2.5× speed is also documented in the same release, no code changes required to use it.
  • Skeptic check: "Adaptive" thinking means the model decides when to reason, not you — hard to audit which turns it skipped reasoning on; if correctness matters, instrument your evals to catch silent reasoning omissions at high.

Claude Code Dynamic Workflows spins up to 1,000 subagents from a natural-language prompt

  • Source: Anthropic — "Introducing dynamic workflows in Claude Code" blog post, May 28, 2026
  • Link: Introducing dynamic workflows in Claude Code — claude.com
  • TL;DR: Dynamic Workflows (research preview, Claude Code + Opus 4.8 only) takes a plain-English task description and auto-generates a JavaScript orchestration script on the fly. That script fans work out across up to 1,000 subagents (16 running concurrently), runs adversarial verification agents against results before folding them in, and reports a single consolidated answer. You enable it in Claude Code via /effort xhigh. Real-world case study: Jarred Sumner used an early version to port Bun from Zig to Rust — 750,000 lines of Rust, 99.8% of existing tests passing, 11 days from first commit to merge.
  • What to do: Try Dynamic Workflows on your hardest repo-wide tasks (large refactors, cross-file migrations, broad test generation) by typing your task as you normally would and enabling /effort xhigh; because it's a research preview, review every orchestration script before it runs in production and expect rough edges in the adversarial verification step.
  • Why trust it: Official Anthropic launch post with documented hard limits (1,000 total agents, 16 concurrent); the Bun case study is from a named engineer (Jarred Sumner) on their actual codebase, not a controlled benchmark — take it as a ceiling example, not a median result.
  • Skeptic check: Research preview status and auto-generated orchestration scripts mean the system can take unexpected paths; the Bun example is a single high-profile case with an experienced user, not a representative workload sample.
