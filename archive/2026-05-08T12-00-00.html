Claude Code capped Opus 4.7 at 200K context instead of 1M — now fixed

  • Source: Anthropic, Claude Code CHANGELOG, May 7, 2026
  • Link: Claude Code releases — GitHub
  • TL;DR: A bug caused Claude Code to calculate context usage against a 200K window instead of Opus 4.7's actual 1M capacity, making /context show inflated percentages and triggering autocompact five times too early. The May 7 release fixes the denominator. The same release also speeds up /resume on large sessions (up to 67% faster on sessions over 40 MB), adds an xhigh effort level for Opus 4.7 (via /effort, --effort, or the model picker), a worktree.baseRef setting to choose whether isolated worktrees branch from origin/<default> or local HEAD, and a /less-permission-prompts skill that scans past transcripts to build an allow-list of read-only Bash and MCP calls.
  • What to do: Update Claude Code; if you built retries or off-peak workarounds to cope with early autocompaction on Opus 4.7, remove them — the model now has access to its full 1M window. If you run large archived sessions, the /resume speedup alone is worth the update.
  • Why trust it: Official Anthropic Claude Code CHANGELOG; multiple GitHub issues filed by Max-plan users confirmed the 200K denominator bug before the fix shipped.
  • Skeptic check: If you have a custom autoCompact.threshold set to a fraction of what you thought was 200K, recalibrate it against the actual 1M — your effective compaction point has just shifted significantly.

Cursor 3.3: full PR lifecycle stays inside the editor, plans run in parallel

  • Source: Cursor, changelog, May 7, 2026
  • Link: Cursor changelog — cursor.com
  • TL;DR: Three additions to the Agents Window: PR Review lets you take a pull request from creation to merge without leaving Cursor; Build Plan in Parallel lets sub-plans run concurrently instead of sequentially; and Split PRs gives you a split-pane view to manage multiple agents or tasks side by side.
  • What to do: Try PR Review as a replacement for opening GitHub in a browser tab for code review — it closes the context-switch gap between editing and reviewing. If you have agent plans with independent branches of work, enable parallel planning to cut wall-clock time.
  • Why trust it: Official Cursor changelog entry for May 7, 2026; community forum thread confirms feature availability.
  • Skeptic check: PR Review quality varies by repo complexity; on large diffs or monorepos, verify the agent's review surface before relying on it.

Codex agents can now work across browser tabs; Codex-Spark added at 128K context

  • Source: OpenAI, Codex changelog, May 7, 2026
  • Link: Codex changelog — OpenAI Developers
  • TL;DR: Two additions in Codex 0.129.0: a Chrome extension lets Codex agents work across browser tabs in the background in parallel — you control which sites it can access, and it doesn't take over your browser; Codex-Spark is now in research preview for ChatGPT Pro users, text-only with a 128K context window. The same release adds Vim-mode editing in the TUI composer (/vim), a redesigned resume/fork picker, and raw scrollback mode.
  • What to do: Install the Chrome extension if your Codex workflows involve web browsing, scraping, or form-filling; use Codex-Spark for tasks that fit in 128K when you want faster or cheaper inference than the full Codex model. Verify your team's acceptable-use policy allows browser-level agent access before rolling the extension out broadly.
  • Why trust it: Official OpenAI Codex changelog; version 0.129.0-alpha.15 confirmed in the OpenAI developer changelog for May 7, 2026.
  • Skeptic check: Codex-Spark is text-only and in research preview — billing model and capability bounds will likely change; don't architect production workflows around its current behavior.

MCP blueprint pattern: agent reasons once, all future runs cost near-zero tokens

  • Source: Parmar, arXiv:2605.00827, May 2026
  • Link: Separating Intelligence from Execution: A Workflow Engine for MCP — arXiv
  • TL;DR: In the usual approach, an agent reasons about every MCP tool call every time it runs, spending tokens proportional to how many actions it takes — even for tasks it has solved before. This paper proposes having the agent reason once to produce a declarative JSON blueprint (a directed sequence of MCP tool calls with loops, parallel branches, and data piping), then execute all future runs via a single run_workflow call with near-zero reasoning overhead. The author reports over 99% token reduction per re-execution and deterministic, idempotent results.
  • What to do: Watch this; no action yet. If you run MCP-heavy agents on the same repeating workflow (scheduled CI checks, nightly data pipelines, recurring test suites), the blueprint pattern is worth prototyping — but it requires building a custom MCP orchestration layer, which is not off-the-shelf today.
  • Why trust it: Single researcher; tested on a graph with 1,200+ nodes and 2,800+ relationships. No independent replication yet.
  • Skeptic check: The 99% token saving is against repeated reasoning, not against a cached or memoized baseline; real-world savings depend on how stable the workflow stays between runs — any change to the task requires re-reasoning.
