Subagent summaries now cached, cutting ~3× per-subagent cost in Claude Code

  • Source: Anthropic, Claude Code v2.1.140, May 13, 2026
  • Link: Claude Code v2.1.140 — GitHub releases
  • TL;DR: Sub-agent progress summaries now participate in prompt caching, dropping the cache_creation token charge when subagents report back to the orchestrator by roughly 3×. The same release makes subagent_type in the Agent tool case- and separator-insensitive, so "Code Reviewer" and "code-reviewer" now resolve to the same agent without a tool-match failure. Also fixed: /goal no longer hangs silently when disableAllHooks or allowManagedHooksOnly is set — it now shows a clear message instead of an indicator that never resolves.
  • What to do: Update to v2.1.140 (npm update -g @anthropic-ai/claude-code) and check your token dashboard after the next multi-subagent session; if you maintain agent configuration files that specify subagent_type, the casing enforcement is now gone, but align them to the canonical kebab-case names anyway to stay readable.
  • Why trust it: Official Anthropic release; "~3×" figure sourced from ClaudeWorld v2.1.140 release notes and May 2026 Claude Code update documentation, consistent with earlier search results. The subagent_type matching change is confirmed from multiple changelog summaries.
  • Skeptic check: The 3× figure is an average across workloads; actual savings depend on subagent summary length and how often the cache is hit in your specific session structure — short summaries or low-repetition workloads will see less benefit.

Cursor cloud agents now run in version-controlled, secret-scoped dev environments

  • Source: Cursor, blog post and changelog, May 13, 2026
  • Link: Development environments for your agents — Cursor blog
  • TL;DR: Cursor cloud agents now run inside Dockerfile-based development environments you configure once and reuse across sessions. Multi-repo support lets one environment contain all the repos an agent needs, eliminating per-session setup. Build layer caching makes environment rebuilds 70% faster when only some layers change. Secrets are scoped per-environment so agents in one environment cannot read another's credentials. Every environment has a version history you can review and roll back, and admins can restrict rollback to admins only. An audit log captures every team member's environment changes.
  • What to do: If you're running Cursor cloud agents on ad-hoc setups, migrate to a Dockerfile-based environment this week: you get free reproducibility, instant rollback if an environment change breaks agents, and secret isolation without any extra configuration beyond scoping secrets at creation time.
  • Why trust it: Official Cursor blog post and changelog from May 13, 2026; 70% build speed improvement stated in the Cursor changelog; details consistent across cursor.com changelog, StartupHub.ai summary, and the Cursor community forum thread on multi-repo support.
  • Skeptic check: The 70% faster rebuild figure applies only when your Dockerfile has cacheable layers that are actually reused — single-step Dockerfiles or frequently changed base layers won't see this gain.

Gemini CLI v0.42.0 drafts reusable agent skills from your past sessions

  • Source: Google / Gemini CLI, v0.42.0 and v0.43.0-preview.0, May 12, 2026
  • Link: Gemini CLI v0.42.0 — GitHub releases
  • TL;DR: Gemini CLI v0.42.0 introduces Auto Memory Inbox: the tool mines your past sessions in the background and proposes durable memory updates and reusable Agent Skills, which you review and promote via /memory inbox. The concurrent v0.43.0-preview.0 adds surgical code edits (the model is now steered toward the edit tool for targeted changes, reducing how much of the file it rewrites and how many context tokens it consumes) and session portability (export a chat session to a file; import it in another terminal via a CLI flag).
  • What to do: Enable Auto Memory ("experimental": { "autoMemory": true } in settings.json), run a week of normal sessions, then review /memory inbox before manually adding memories — it may surface patterns you'd otherwise write by hand. If you're on the preview channel, surgical code edits reduce token waste on large-file edits with no prompt change needed.
  • Why trust it: Official Gemini CLI GitHub release page; Auto Memory mechanics confirmed in geminicli.com docs; surgical code edits and session portability confirmed in the v0.43.0-preview.0 changelog. The Gemini CLI project is Google-maintained and open-source.
  • Skeptic check: Auto Memory is still experimental; skills it proposes are inferred from session patterns and may generalize incorrectly from debugging sessions or one-off tasks — review each proposal before promoting it.

LLM CLI 0.32a2 shows GPT-5 reasoning tokens inline during tool calls

  • Source: Simon Willison, simonwillison.net, May 12, 2026
  • Link: Release: llm 0.32a2 — Simon Willison
  • TL;DR: LLM 0.32a2 switches reasoning-capable OpenAI models from /v1/chat/completions to the /v1/responses endpoint, which enables interleaved reasoning across tool calls for GPT-5 class models. Summarized reasoning tokens now stream to stderr in a distinct color between tool invocations, so you can see exactly why the model chose a tool or constructed unusual arguments. Pass -R or --hide-reasoning to suppress them. Also fixed: tool-calling conversation histories were not correctly restored from SQLite, causing broken multi-turn tool sessions.
  • What to do: Update (pip install -U llm), run a GPT-5 model with tool calls, and watch the reasoning output to debug unexpected tool selections or argument construction — it replaces the guessing you'd otherwise do when a tool call fails silently.
  • Why trust it: Simon Willison is the author and maintainer of the LLM CLI tool; this is his own release announcement for a version he shipped. The /v1/responses endpoint switch is a factual API change, not a measurement. The SQLite bug fix is a regression addressed in this release.
  • Skeptic check: The reasoning visibility applies only to OpenAI GPT-5 class models via the /v1/responses endpoint — other providers (Anthropic, Gemini, etc.) continue using their existing endpoints and are unaffected by this change.

Larger models don't consistently beat small ones on tool calls; cheap models can cost more

  • Source: Microsoft Research & Stanford, arXiv:2605.07112, submitted May 8, 2026
  • Link: Switchcraft: AI Model Router for Agentic Tool Calling — arXiv
  • TL;DR: Across five standard tool-calling benchmarks, bigger models do not consistently outperform smaller ones on tool-use tasks. More practically: a nominally cheaper model can end up costing more per task than a larger model if it generates many more reasoning tokens before each tool call. The paper's routing system (Switchcraft, not yet a product) achieves accuracy matching the best individual model while cutting inference cost 84% by picking the smallest capable model per call.
  • What to do: Before defaulting to your largest model for agent tool use, run a quick benchmark on your actual tool catalog with a smaller model — and measure total tokens per task completion, not just per-token price, since reasoning-heavy smaller models can cost more end-to-end than a faster, less verbose larger model.
  • Why trust it: Evaluated on ~13,000 API calls across 12 models on five function-calling benchmarks by Microsoft Research and Stanford; independent benchmarks, not vendor-reported. Submitted May 8, 2026.
  • Skeptic check: The benchmarks are synthetic function-calling tasks; how well the "smaller model often suffices" finding transfers to production agent catalogs with many overlapping or ambiguously described tools has not been measured.
