Idle background sessions now keep their config

  • Source: Anthropic, Claude Code v2.1.143, May 15, 2026
  • Link: Claude Code v2.1.143 — GitHub releases
  • TL;DR: When a background session wakes from idle, it now retains the model and effort level you set — instead of resetting to defaults. Separately, /bg now also preserves --mcp-config, --settings, --add-dir, --plugin-dir, and --strict-mcp-config across session respawn, so your MCP servers and non-default settings survive the full background session lifecycle.
  • What to do: Update to v2.1.143 and stop hard-coding model and effort redundantly in every background task definition — the settings will stick across idle cycles and respawns.
  • Why trust it: Official Anthropic release, confirmed across multiple independent changelog trackers (Releasebot, ClaudeLog, developertoolkit.ai); GitHub releases page was inaccessible but details matched across at least three independent search-snippet sources.
  • Skeptic check: Only affects sessions you have backgrounded via /bg; foreground sessions have always preserved these settings.

Claude Code now enforces plugin dependency order

  • Source: Anthropic, Claude Code v2.1.143, May 15, 2026
  • Link: Claude Code v2.1.143 — GitHub releases
  • TL;DR: claude plugin disable <name> now refuses if another currently-enabled plugin depends on the target, and prints a copy-pasteable command to disable the entire dependency chain at once. Going the other way, claude plugin enable <name> now force-enables all transitive dependencies automatically.
  • What to do: If you have a multi-plugin setup where one plugin wraps or depends on another, test claude plugin disable after updating — the hint output will show you the exact chain to run if the command refuses.
  • Why trust it: Official Anthropic release, described identically across multiple independent changelog trackers.

Plugin marketplace now shows projected token costs

  • Source: Anthropic, Claude Code v2.1.143, May 15, 2026
  • Link: Claude Code v2.1.143 — GitHub releases
  • TL;DR: The /plugin marketplace browse pane now shows per-turn and per-invocation token cost estimates for each plugin before you install it. This is the first time you can compare token overhead across plugins at browse time rather than discovering costs after installation and seeing it in your billing.
  • What to do: Before adding new plugins to a cost-sensitive workflow, open /plugin marketplace and check the per-turn estimates; high-cost plugins are candidates for selective enabling per task type rather than always-on.
  • Why trust it: Official Anthropic release, consistent across multiple changelog sources.
  • Skeptic check: These are estimates, not hard caps; actual token use will vary with context window size and model.

New setting skips worktrees for background sessions

  • Source: Anthropic, Claude Code v2.1.143, May 15, 2026
  • Link: Claude Code v2.1.143 — GitHub releases
  • TL;DR: Setting worktree.bgIsolation: "none" in your Claude Code config lets background sessions edit the working copy directly rather than spinning up an EnterWorktree step first. The setting exists specifically for repos where git worktrees are impractical — monorepos with complex toolchains, repos that inline submodules, and similar setups.
  • What to do: If background sessions are failing or slow because of worktree setup in a repo that can't support isolated worktrees cleanly, add worktree.bgIsolation: "none" to your project settings.json — but understand this trades isolation for compatibility; concurrent background sessions in the same repo can now conflict.
  • Why trust it: Official Anthropic release; feature described consistently and precisely across sources.
  • Skeptic check: Disabling isolation is a compatibility escape hatch, not a recommended default; concurrent background sessions become unsafe.

Claude Code PowerShell now bypasses execution policy

  • Source: Anthropic, Claude Code v2.1.143, May 15, 2026
  • Link: Claude Code v2.1.143 — GitHub releases
  • TL;DR: The PowerShell tool now passes -ExecutionPolicy Bypass automatically, so scripts and tools silently blocked by a restrictive policy on Windows/WSL now run. Set CLAUDE_CODE_POWERSHELL_RESPECT_EXECUTION_POLICY=1 to opt out and restore the previous behavior.
  • What to do: If PowerShell-based tools have been silently failing in Claude Code on Windows, update to v2.1.143 — you no longer need to pre-configure execution policy separately. If your environment has a security requirement that the restricted policy be enforced, set the opt-out env var before updating.
  • Why trust it: Official Anthropic release; change is unambiguous and independently verifiable by testing script execution before and after update.
  • Skeptic check: Bypass mode runs scripts regardless of source; on managed corporate Windows machines, confirm with your security team before deploying.

Weak API descriptions cause most MCP agent failures

  • Source: Lima et al., arXiv:2605.14312, submitted May 14, 2026
  • Link: arXiv:2605.14312 — Making OpenAPI Documentation Agent-Ready
  • TL;DR: A team wrapping 16 production REST APIs (~600 endpoints) as MCP tools found that APIs which worked fine as microservices caused consistent agent failures at task planning, tool selection, and payload construction — not because of model limitations, but because of documentation quality problems: vague descriptions, explanations split across unrelated fields, and endpoints that mixed multiple concerns. They built a multi-agent detection tool (Hermes) that scans OpenAPI specs and generates per-endpoint diagnostic reports flagging these issues.
  • What to do: Before exposing a REST API as an MCP tool, treat your OpenAPI description text as prompt input: each endpoint description should state one thing clearly, avoid mixing operational concerns, and provide enough context that an agent can correctly choose it over similar-looking endpoints. Run an LLM pass over your OpenAPI spec looking specifically for vague verbs, missing payload semantics, and descriptions that copy the endpoint path rather than explaining behavior.
  • Why trust it: Industrial study on 16 production APIs / ~600 endpoints; failures measured against actual agent task-completion, not synthetic benchmarks. Full paper text was behind a fetch block — key findings confirmed from arXiv abstract and multiple search snippets; the specific smell taxonomy and numeric detection rates were not verified from the full text.
  • Skeptic check: Study was conducted in one microservice architecture; whether the same documentation issues cause failures in directly-authored MCP servers (rather than REST-to-MCP wrappers) is not established by this work.

Grok Build evaluates competing agents before delivery

  • Source: xAI, Grok Build early beta, announced May 14–15, 2026
  • Link: xAI release notes — docs.x.ai
  • TL;DR: xAI launched Grok Build, a terminal coding agent (currently early beta, SuperGrok Heavy subscribers only), whose defining architecture feature is Arena Mode: instead of returning a single solution, it runs up to eight parallel agents on the same problem, scores and ranks their outputs automatically, and only then surfaces the result to the developer. The tool is local-first — source code is not sent to xAI servers. The underlying model is grok-code-fast-1.
  • What to do: Watch this; no action yet — the Arena Mode pattern (run N agents against the same problem, rank internally before human review) is the useful architectural idea here, independent of the specific tool. If you're designing a code-generation harness, this is the competitive-evaluation pattern to evaluate for your own multi-agent workflows.
  • Why trust it: Multiple independent news sources (Engadget, CIO Dive, Android Headlines, Dataconomy) all reporting on xAI's own announcement; technical details consistent across sources. SWE-Bench figure excluded per hard-exclude rule.
  • Skeptic check: Early beta, high-cost subscriber tier only; Arena Mode runs up to 8× agent cost per task — whether the quality of ranked results justifies the cost has no independent evidence yet.
