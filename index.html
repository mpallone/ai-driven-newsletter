Claude Code v2.1.187 blocks sandboxed commands from reading credentials

  • Source: Anthropic — Claude Code GitHub releases
  • Link: Claude Code releases — github.com/anthropics/claude-code
  • TL;DR: v2.1.187 (released June 23 at 21:03 UTC) adds a sandbox.credentials setting that prevents shell commands running inside Claude Code's sandbox from reading credential files and secret environment variables. The same release lets org admins configure which models appear in the model picker, --model flag, /model command, and ANTHROPIC_MODEL env var — so an org can lock Claude Code to approved models fleet-wide. A bug fix in this release also resolves structured output failures when using --json-schema or workflow agent({schema}).
  • What to do: Add sandbox.credentials to your project or user settings.json to prevent sandboxed shell commands from accidentally reading ~/.aws/credentials, ~/.netrc, or secret env vars — check the GitHub release notes directly since the official docs have not yet been updated (a GitHub issue tracking the documentation gap is open at issue #70440).
  • Why trust it: First-party Anthropic GitHub release tagged v2.1.187, dated June 23, 2026; existence of the documentation gap confirmed by a GitHub issue filed against the anthropics/claude-code repo the same day.
  • Skeptic check: The setting's accepted values, default state, and the exact list of credential files and env var patterns it blocks are not yet documented — test behavior in a controlled environment before relying on it for a security boundary.

Claude Tag stores credentials outside the agent and injects them at the network boundary

  • Source: Anthropic — Agent identity: a new access model for autonomous, team-wide AI
  • Link: Agent identity: a new access model for autonomous, team-wide AI — Anthropic, June 24, 2026
  • TL;DR: Anthropic launched Claude Tag on June 23 — an always-on Claude that lives in Slack as a shared team agent — and published a separate post on June 24 detailing the agent identity architecture underneath it. The key design: each channel gets its own isolated agent identity (an org-level service account, not any user's credential). A component called Agent Proxy stores tool credentials separately from both the model and the code execution sandbox; at the moment of an outbound request, Agent Proxy injects the credential at the network boundary and checks the destination against admin-configured allow rules. The default is deny: a host is unreachable from the sandbox until an admin explicitly allows it. Credentials are stored once and never shown again; the model and sandbox never hold them directly. Actions appear under the service account in connected tools' audit logs. Claude Tag retires the older Claude in Slack integration on August 3, 2026.
  • What to do: When building multi-user agent systems that need credential management, adopt the pattern: store credentials in a separate proxy component, never pass them to the agent runtime or model, inject them at the outbound request boundary, and default to deny for all outbound destinations until an admin explicitly allowlists them — this gives you a clean audit trail and limits blast radius if the agent is manipulated.
  • Why trust it: First-party Anthropic launch announcement (June 23) and engineering blog post (June 24); architectural details confirmed in the Claude Tag docs at claude.com/docs/claude-tag/concepts/agent-identity; Anthropic states their own product teams route ~65% of code changes through an internal version of this system.
  • Skeptic check: Claude Tag is not air-gapped — tool inputs and outputs still flow through Anthropic's control plane (where Claude runs), so sensitive data in tool responses reaches Anthropic infrastructure; it is explicitly not ZDR- or HIPAA-BAA-eligible.

Codex Security validates each vulnerability in an isolated environment before surfacing it

  • Source: OpenAI — Scaling Trusted Access for Cyber with GPT-5.5 and GPT-5.5-Cyber
  • Link: Scaling Trusted Access for Cyber with GPT-5.5 and GPT-5.5-Cyber — OpenAI, June 23, 2026
  • TL;DR: OpenAI's Codex Security plugin moved out of research preview on June 23 for ChatGPT Enterprise, Business, Pro, and Edu users. Its workflow has three stages: (1) the agent builds a threat model for your repo and finds candidate vulnerabilities, (2) an automated validator tries to reproduce each finding in an isolated sandbox — findings that can't be reproduced there are dropped before they reach you, (3) only confirmed findings surface with a suggested patch for human review; the patch goes to a PR, it does not auto-apply. In the first week of the companion Patch the Planet program (scanning open-source projects), the system generated 64 pull requests across 19 projects. OpenAI's own security FAQ for Codex Security notes that untrusted repository content is a prompt injection vector for the agent doing the scanning.
  • What to do: When building code-analysis agents that surface findings to users, add an automated reproduction stage between detection and surfacing — run each finding against the actual codebase in an isolated environment and drop it if it can't be reproduced; this eliminates noise, forces the agent to produce concrete evidence rather than speculation, and reduces user alert fatigue.
  • Why trust it: First-party OpenAI launch announcement June 23, 2026; Patch the Planet first-week counts stated by OpenAI; the research preview scanned 30M commits across 30,000 codebases per OpenAI's own figures.
  • Skeptic check: OpenAI itself flags that attacker-controlled repository code can be a prompt injection vector for the scanning agent — the validate step runs untrusted code, which means a malicious repo could potentially manipulate the agent's conclusions about what constitutes a vulnerability.

The rule "arXiv submissions from the last 7 days" misses high-signal conference papers whose preprints are slightly older than 7 days but whose public discussion is brand-new.
