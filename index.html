Anthropic publishes a decision tree for CLAUDE.md vs. skills vs. hooks vs. subagents

  • Source: Anthropic (claude.com/blog)
  • Link: Steering Claude Code: skills, hooks, rules, subagents, and more — Anthropic
  • TL;DR: Anthropic laid out, in one place, when to reach for each of Claude Code's seven steering mechanisms — CLAUDE.md, rules, skills, subagents, hooks, output styles, and system-prompt appends — based on whether you want visibility into each step, isolation from the main conversation, or hard deterministic enforcement.
  • What to do: Use their rule of thumb — skill for an in-thread visible procedure, subagent for noisy side-work you don't need to review, hook for deterministic enforcement, output-style or system-prompt-append only for narrow high-weight changes — to sanity-check your own harness's mechanism choices.

  • Skeptic check: It's vendor guidance, not a measured comparison — no data on outcomes for picking the "wrong" mechanism.

Anthropic names four ways to structure an agent loop

  • Source: Anthropic (claude.com/blog)
  • Link: Getting started with loops — Anthropic
  • TL;DR: Anthropic's guide names four agent-loop shapes — one-shot/turn-based, goal-checked, scheduled, and event-triggered — and explains when to use each instead of open-ended "keep going" prompting.
  • What to do: Compare your own harness's stop-condition logic to this taxonomy — for open-ended maintenance work, check progress against an explicit goal with a separate evaluator instead of trusting the acting model's own sense of "done."

  • Skeptic check: No failure-rate data or comparison against other harnesses' loop designs — it's a design taxonomy, not an evaluation.

Model behavior & reliability

One case where a newer model got worse at a core agent skill, and one benchmark suggesting the priciest model isn't always the cheapest per finished task.

Newer Claude models sometimes invent fake fields in tool calls

  • Source: Armin Ronacher (maintainer of the Pi coding harness); discussed on Hacker News
  • Link: Better models, worse tools — Armin Ronacher
  • TL;DR: Claude's newest models occasionally add extra, made-up fields when calling a custom code-editing tool that isn't shaped like Claude Code's own — breaking the call — likely because they've been trained hard on Claude Code's specific edit-tool format at the expense of others.
  • What to do: If your harness uses a custom edit or patch tool schema rather than Claude Code's flat old-string/new-string shape, add strict schema validation and specifically test edit-tool reliability on Opus 4.8 and Sonnet 5 before upgrading.
  • Why trust it: A firsthand production report from a harness maintainer, corroborated by a GitHub issue on the Pi repo quantifying roughly a 20% malformed-edit rate in one test run, plus a 221-point, 78-comment Hacker News thread.
  • Skeptic check: Small, informal sample — one maintainer's harness, roughly ten trials; the "trained too hard on Claude Code's schema" explanation is the author's theory, not confirmed by Anthropic.

An open-weight model matched Opus on real internal code tasks for less money

  • Source: Databricks Engineering Blog
  • Link: Benchmarking coding agents on Databricks' multi-million-line codebase — Databricks
  • TL;DR: Databricks ran coding agents against real internal engineering tasks on its own multi-million-line codebase, not a public leaderboard, and found open-weight GLM-5.2 performed about as well as Claude Opus 4.8 while costing roughly a third less per completed task.
  • What to do: Benchmark cost per completed task on your own representative tasks instead of trusting per-token list price or public leaderboards — Databricks' data shows the price ranking can flip once reasoning-token overhead is counted in.
  • Why trust it: An internal benchmark built from real engineering tasks, run end-to-end against a large multi-language codebase, with a published task-complexity breakdown.
  • Skeptic check: Self-reported by a vendor that sells its own competing agent/router product; the task set isn't open for independent audit.

Agent security

Two disclosures this week target the parts of the agent loop that read untrusted text and guess names, not the model itself.

One phrase tricked GitHub's AI agent into leaking private repos

  • Source: Noma Security
  • Link: GitLost: how we tricked GitHub's AI agent into leaking private repos — Noma Security
  • TL;DR: Anyone could post a public GitHub issue with hidden instructions, prefix it with the word "Additionally," and trick GitHub's Agentic Workflows feature into copying private-repo data somewhere the attacker could see it.
  • What to do: If an agent in your pipeline reads untrusted issue or PR text, treat that text as untrusted instructions, not just untrusted data — don't rely on a vendor's built-in prompt-injection filter alone, and add your own controls on what the agent is allowed to read versus act on.
  • Why trust it: A concrete, responsibly disclosed working exploit against a specific shipped feature, described with the exact guardrail-bypass mechanism.
  • Skeptic check: Disclosed by a commercial AI-security vendor with an interest in selling detection tooling; unclear from secondary coverage whether GitHub has already shipped a fix — check GitHub's current advisory before assuming the bypass still works.

Agents hallucinate repo names attackers can register first

  • Source: Researchers at Tel Aviv University, Technion, and Intuit
  • Link: Beware of Agentic Botnets — research project page
  • TL;DR: When asked to fetch a "trending" repo or skill, coding agents often invent a plausible name that doesn't exist, and attackers can predict those exact fake names and register them first, so the agent fetches attacker-controlled code instead — a pattern the researchers found across nine tools, including Cursor, Windsurf, Gemini CLI, and GitHub Copilot.
  • What to do: Never let an agent auto-clone or auto-install a repo, package, or skill it named itself from a vague request — require a human to confirm the exact URL against a known-good source first.
  • Why trust it: Multi-institution academic research testing nine named production tools, with hallucination rates reported up to 85% for repo-cloning prompts and 100% for skill-fetch prompts.
  • Skeptic check: The rates come from the researchers' own test prompts, which may skew toward worst-case phrasing rather than typical usage, and haven't yet been independently replicated.

Practitioner notes

One real cost data point for an agent-driven refactor, and one method for testing whether prompt-section order actually matters.

Real numbers for an agent-driven library refactor: 37 prompts, about $149

  • Source: Simon Willison
  • Link: sqlite-utils, refactored by Fable — Simon Willison
  • TL;DR: Simon Willison had an AI coding agent do most of the work refactoring his sqlite-utils library and published exactly what it cost and how it went, including a silent transaction bug the agent caught along the way.
  • What to do: Use this as a rough cost and process benchmark — 37 prompts, 34 commits, about $149.25 — when budgeting or justifying an agent-driven refactor of real production code.
  • Why trust it: First-person account from the library's own maintainer, with concrete, checkable numbers rather than a vague impression.
  • Skeptic check: One case study, one maintainer, one library, with no comparison to how long or how much a human-only refactor would have cost.

Prompt section order changes output — and you can test it systematically

  • Source: Duoduo Danny Ying, Alan R. Vazquez, Hongquan Xu (arXiv)
  • Link: Prompt engineering using order-of-addition experiments — arXiv
  • TL;DR: The order you place pieces of a prompt in can measurably change how well a model does the task, and the authors borrow a statistical technique for testing different orderings systematically instead of guessing.
  • What to do: If you're tuning the structure of a long system prompt, run a small structured ordering test — swap the position of a couple of sections and compare — rather than assuming your first draft's ordering is already best; there's no ready-made tool yet, so treat this as a method to borrow, not a plug-in fix.
  • Why trust it: A reproducible experimental method applied to real model outputs on a defined task, not just anecdote.
  • Skeptic check: The demonstrated task is narrow (generating statistical experiment designs) — how well the ordering effect generalizes to long agentic system prompts or tool-heavy contexts is untested.
