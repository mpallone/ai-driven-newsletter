Claude Code was silently duplicating skill instructions in context

  • Source: Anthropic — Claude Code CHANGELOG.md
  • Link: Claude Code CHANGELOG — v2.1.202, GitHub
  • TL;DR: Before v2.1.202 (July 6), if a skill you'd already loaded got invoked again in the same session, Claude Code appended a second full copy of its instructions into context instead of reusing the first one — a silent, compounding token cost for anyone using slash-skills repeatedly in a long session.
  • What to do: Upgrade to v2.1.202 or later if you build or rely on skills that get invoked more than once per session, since older versions are quietly burning context on every repeat call.
  • Why trust it: Stated directly in Anthropic's own CHANGELOG.md as a fixed bug in the v2.1.202 entry, dated to the July 6, 2026 release.
  • Skeptic check: The changelog doesn't quantify how much context this wasted in practice — treat it as "fixed a real duplication bug," not "you were burning X% of your budget."

Claude Code adds a knob for how many agents a workflow spawns

  • Source: Anthropic — Claude Code CHANGELOG.md
  • Link: Claude Code CHANGELOG — v2.1.202, GitHub
  • TL;DR: v2.1.202 (July 6) adds a "Dynamic workflow size" setting in /config that nudges Claude toward smaller, medium, or larger agent fleets when it builds a dynamic workflow — it's an advisory guideline the model leans on, not a hard cap.
  • What to do: If your dynamic workflows have been spawning more parallel agents (and burning more tokens) than a task warrants, set this to "small" as a default and override per-workflow when you actually need the fan-out.
  • Why trust it: Directly from Anthropic's CHANGELOG.md, v2.1.202 entry, July 6, 2026.
  • Skeptic check: Because it's advisory rather than enforced, a complex task can still spawn a large fleet even on the "small" setting — don't rely on it as a hard cost ceiling.

Claude Code subagents no longer lose their work when you tab away

  • Source: Anthropic — Claude Code CHANGELOG.md
  • Link: Claude Code CHANGELOG — v2.1.203, GitHub
  • TL;DR: v2.1.203 (July 7) fixes a bug where returning to the claude agents list would silently kill any running subagents and restart their prompt from scratch, discarding whatever they'd already produced; the same release also stops worktree-isolated subagents from occasionally running shell commands in the parent checkout instead of their own worktree.
  • What to do: Upgrade if you run multi-subagent sessions and have been intermittently losing subagent output for no obvious reason — this was likely the cause, not a flaky prompt.
  • Why trust it: Directly from Anthropic's CHANGELOG.md, v2.1.203 entry, dated July 7, 2026 — a long release with 30+ background-agent and worktree-isolation fixes.

Codex CLI now loads MCP tool schemas on demand, not all upfront

  • Source: OpenAI — Codex CLI GitHub release notes
  • Link: Codex CLI rust-v0.143.0 release notes, GitHub
  • TL;DR: As of rust-v0.143.0 (July 8), Codex's MCP tools default to "tool search" — schemas for connected MCP servers are searched and loaded into context as needed rather than all being dumped into the system prompt up front, which is the same on-demand pattern Claude Code's deferred-tool search uses.
  • What to do: If you connect many MCP servers to Codex and noticed a bloated system prompt or slower first response, this default change should shrink your baseline context footprint — verify it's on and don't manually pre-load tool lists out of habit.
  • Why trust it: From OpenAI's own GitHub release notes for the dated rust-v0.143.0 build (July 8, 2026).
  • Skeptic check: The release notes don't give a before/after token count, so the size of the context savings for a typical multi-MCP setup is unverified.

A live GitHub issue is tracking a GPT-5.5 Codex reasoning glitch

  • Source: openai/codex GitHub issue #30364, amplified on Hacker News
  • Link: GPT-5.5 Codex reasoning-token clustering at 516/1034/1552 — GitHub issue #30364
  • TL;DR: A Codex user found that GPT-5.5's reasoning length clusters suspiciously often at exactly 516 tokens (and multiples of it), a pattern barely present in GPT-5.2/5.3/5.4, and reasoning runs that land exactly on 516 tokens are disproportionately likely to give the wrong answer on complex tasks.
  • What to do: Watch this; no action yet — the reporter is explicit that this doesn't prove hidden reasoning-budget truncation, only that Codex's own telemetry shows a GPT-5.5-specific anomaly worth a second, independent look before you change how you use the model.
  • Why trust it: One engineer's analysis of Codex-internal telemetry, reporting an exact-516-token clustering rate of 44.0% for GPT-5.5 versus 0.34% for GPT-5.2 and ~0% for Codex-specific GPT-5.3 variants — a single-source, self-reported statistic, not an independently reproduced study.
  • Skeptic check: The clustering is correlational, not a controlled experiment, and the "wrong answer" link is based on a task-level anecdote rather than a matched before/after comparison — a hidden confound (e.g., harder prompts triggering both shorter reasoning and wrong answers) hasn't been ruled out.

Newer Claude models are worse at calling non-Anthropic coding tools

  • Source: Armin Ronacher (lucumr.pocoo.org), amplified by Simon Willison
  • Link: Better Models: Worse Tools — Simon Willison, linking to Armin Ronacher's original post
  • TL;DR: Building his own coding harness "Pi," Armin Ronacher found that Opus 4.8 and Sonnet 5 call his custom edit tool with extra, invented fields that don't match his schema — a problem older Claude models didn't have — and his working theory is that Anthropic's newer models were specifically trained to nail Claude Code's own edit-tool format, at the cost of getting sloppier with anyone else's.
  • What to do: If you run a custom coding agent with your own edit/file tool schema, add explicit validation and a clear retry-with-guidance error message for malformed tool calls now, rather than assuming newer Claude models will keep matching your schema as well as older ones did.
  • Why trust it: One developer's first-hand debugging of his own harness's tool-call logs, no formal sample size; picked up and editorially endorsed by Simon Willison and discussed on Hacker News and Lobsters.
  • Skeptic check: It's one person's harness and anecdotal before/after impression across model versions, not a controlled comparison — the "trained specifically toward Claude Code's format" explanation is Ronacher's hypothesis, not something Anthropic has confirmed.

A five-question quiz can force you to actually understand agent-written code

  • Source: Geoffrey Litt (geoffreylitt.com), amplified by Simon Willison
  • Link: Understand to participate — Simon Willison, linking to Geoffrey Litt's original post
  • TL;DR: Geoffrey Litt argues that once an agent can write code faster than you can read it, your bottleneck shifts to whether you understand the system well enough to keep steering it — his daily practice is a /explain-diff skill that turns a diff into a structured explainer (background, core intuition, walkthrough) followed by a five-question quiz, with a personal rule not to send code out until he passes it.
  • What to do: Build or adopt an "explain this diff, then quiz me on it" skill for your own agent workflow before merging agent-generated changes you haven't personally traced through.
  • Why trust it: A single practitioner's self-reported daily workflow on his own projects, with no external measurement of how much it improves review quality or catches bugs.
  • Skeptic check: There's no comparison against reviewers who skip the quiz, so whether it meaningfully changes bug-catch rates versus just reading the diff carefully is untested.

Tencent open-sourced the first scanner built for MCP and agent-skill supply chains

  • Source: Tencent Zhuque Lab, via Hugging Face Daily Papers
  • Link: Securing the AI Agent: A Unified Framework for Multi-Layer Agent Red Teaming — Hugging Face Papers
  • TL;DR: Tencent released AI-Infra-Guard, an open-source tool that specifically audits MCP servers and agent-skill packages (not just the underlying model), and paired it with SkillTrustBench, a benchmark built from 62,652 real skills pulled off public marketplaces, to measure how trustworthy those skills actually are and how well scanners catch the bad ones.
  • What to do: If you install third-party MCP servers or agent skills from public marketplaces, run them through a supply-chain scanner like this before granting them tool access, the same way you'd scan a new npm dependency.
  • Why trust it: Tencent's own technical report, distilling 5,520 evaluation cases from 62,652 collected skills across nine threat categories; the paper surfaced on Hugging Face's Daily Papers on July 6, 2026, but is Tencent's self-reported evaluation of its own tool, not an independent audit.
  • Skeptic check: Benchmark and scanner come from the same team, which is a conflict of interest for an "effectiveness" claim — an independent group re-running SkillTrustBench against competing scanners would be more convincing.
