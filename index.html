Exposing fewer tools at each agent step cuts token use 90% and near-eliminates wrong-tool calls

  • Source: Rahul Suresh Babu and Laxmipriya Ganesh Iyer — arXiv:2606.06284, submitted June 4, 2026
  • Link: ToolChoiceConfusion: Causal Minimal Tool Filtering for Reliable LLM Agents — arXiv
  • TL;DR: Giving an agent access to all available tools at every step reliably degrades performance: more choices create more wrong-tool calls and more tokens spent on tool descriptions the model doesn't need yet. The paper proposes Causal Minimal Tool Filtering (CMTF), which annotates each tool with a lightweight precondition-effect contract and exposes only the tools whose preconditions are met in the current task state. On multi-step tool-use tasks, this cuts average token usage from 24,569 to 2,405 per task and reduces wrong-tool calls from 1.25 to 0.01 per task.
  • What to do: Add precondition-effect annotations to your tool definitions (what state must be true before this tool can run, and what changes after it does), then build a filtering layer in your harness that only injects tools whose preconditions the current task state satisfies — even a coarse manual version of this will outperform exposing everything.
  • Why trust it: Measured on multi-step tool-use tasks comparing CMTF against four baselines: all-tools exposure, keyword retrieval, state-aware filtering without causal contracts, and causal-path ablations; metrics include task success, wrong-tool calls, premature actions, tool exposure count, and token cost. Full paper on arXiv, submitted June 4, 2026.
  • Skeptic check: The benchmark is a controlled multi-step tool-use suite — real production harnesses often have messier state representations and tasks where step boundaries are ambiguous, which could narrow the gains. I couldn't access the full paper directly (403) so specific benchmark names and agent models tested are unverified.

Gemini CLI stops working June 18 — MCP config rename causes silent failures during migration

  • Source: Google Developers Blog — An important update: Transitioning Gemini CLI to Antigravity CLI, published May 19, 2026; Agentpedia migration guide
  • Link: Transitioning Gemini CLI to Antigravity CLI — Google Developers Blog
  • TL;DR: On June 18, 2026, gemini CLI stops serving requests for Google AI Pro, Ultra, and free users — no grace period. The replacement is Antigravity CLI (command: agy). The migration itself takes under 10 minutes, but there is one trap: Gemini CLI stored MCP server config inline in settings.json, while Antigravity CLI uses a separate mcp_config.json. If you copy the block over without renaming the field url to serverUrl for remote servers, MCP connections fail silently with no error output. Enterprise Gemini Code Assist Standard/Enterprise licenses are exempt from the June 18 cutoff.
  • What to do: Before June 18: install agy, move MCP server config out of settings.json into a new mcp_config.json, and rename every url field to serverUrl for remote MCP entries — then run a test tool call to confirm servers connect before the deadline.
  • Why trust it: Primary source is the official Google Developers Blog post (May 19, 2026) announcing the June 18 cutoff; the silent-failure trap on the url→serverUrl rename is documented in multiple independent migration guides that reverse-engineered the behavior from the new config schema.
  • Skeptic check: Google has extended deadlines before (Gemini Enterprise toggle slipped by one day to June 9); if you're close to the wire, check the official blog post for any last-minute extensions.
