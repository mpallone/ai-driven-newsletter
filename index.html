Devin Desktop scopes MCP grants per server

  • TL;DR: Devin Desktop shipped changes giving subagents their own default-model setting and direct MCP tool access, and letting users grant MCP tool permissions per-server rather than per-tool, with grants that persist across sessions instead of re-prompting every time.

Newer Claude models mangle custom tool schemas

  • Source: Armin Ronacher (lucumr.pocoo.org), relayed by Simon Willison
  • Link: Better Models, Worse Tools — Armin Ronacher
  • TL;DR: When Ronacher's own agent harness calls a custom edit tool shaped as an edits[] array with oldText/newText fields — different from Claude Code's flat old_string/new_string — Opus 4.8 and Sonnet 5 invent extra fields that aren't in the schema (like type, id, matchCase) and get the tool call rejected; about 20% of complex, multi-turn edits fail this way, and it's worse on the newer models than on older ones.
  • What to do: If your harness's edit-tool schema doesn't mirror Claude Code's flat old-string/new-string shape, test it directly against the exact model version under real multi-turn history rather than assuming newer models are more schema-compliant; stripping thinking blocks from conversation history roughly halved Ronacher's failure rate, and enabling strict tool-call validation eliminated it entirely.
  • Why trust it: First-hand account from Ronacher (creator of Flask/Jinja2/Werkzeug, now building agentic coding tools) based on his own harness's production failure logs and reproduction runs, relayed without rebuttal by Willison the same day.
  • Skeptic check: This is one team's harness and one schema shape, not a controlled multi-harness benchmark — the ~20% figure may not transfer to a differently-shaped schema, and neither page could be fetched directly this run to confirm exact wording.

AI review catches sqlite-utils data-loss bug

  • Source: Simon Willison
  • Link: Shipping sqlite-utils 4.0 with Claude Fable — Simon Willison

GPT-5.5 Codex reasoning tokens cluster oddly

  • Source: GitHub (openai/codex issue analysis), discussed on Hacker News
  • Link: GPT-5.5 Codex reasoning-token clustering analysis — GitHub
  • TL;DR: An analysis of 390,195 Codex response records found GPT-5.5 responses land on exactly 516 reasoning tokens (with secondary spikes at 1034 and 1552) far more often than any other model, with that exact-516 rate rising from 0.11% in February to 53.3% in May while the average reasoning-token count fell over the same period — and a small independent reproduction found every one of 4 exact-516 runs on a logic puzzle gave a wrong answer.
  • What to do: If you route hard tasks to GPT-5.5 in Codex, check the reasoning_output_tokens field in the response — a value landing exactly on 516, 1034, or 1552 is a cheap signal the model may have cut its reasoning short, and worth auto-triggering a re-run or escalation rather than trusting the output as-is.
  • Why trust it: Large sample (390K records across 865 sessions) with a specific, quantified clustering ratio and a documented trend over time, plus a small independent reproduction showing the same wrong-answer pattern.
  • Skeptic check: The author explicitly stops short of proving hidden reasoning truncation — this could turn out to be a token-counting or logging artifact rather than genuinely worse reasoning; treat the root cause as unconfirmed until OpenAI comments or a larger controlled study replicates the wrong-answer correlation.

Claude Code drops directory rules after compaction

  • Source: GitHub (anthropics/claude-code issue tracker)
  • Link: Claude Code issue #74066 — GitHub
  • TL;DR: A user's initial report of an apparent cross-session content leak in an Enterprise zero-data-retention Claude Code session turned out, on reading the actual thread, to have a more mundane and still-useful explanation: Claude Code was launched from one directory while operating in another, and after a context-compaction event it "forgot" the earlier instruction not to touch the launch directory.
  • What to do: Don't rely on an instruction given earlier in a long session to survive /compact — re-state hard directory or scope constraints after compaction, and use permission/sandbox controls rather than prompt-based restrictions for anything security-sensitive; if you see unexplained content in a session, check the local transcript at ~/.claude/projects/<encoded-cwd>/<session-id>.jsonl before assuming a cross-tenant leak.
  • Why trust it: The GitHub issue was fetched directly this run, including the reporter's own follow-up narrowing the cause and a triage comment distinguishing local context bleed from a genuine cross-account leak.
  • Skeptic check: Anthropic hasn't posted an official root-cause confirmation as of this writing — treat "instruction lost after compaction" as the most likely explanation from the thread itself, not a vendor-confirmed diagnosis.

Coding-agent benchmarks don't reproduce across machines

  • Source: arXiv (Chen, Sun, Shi, Lo, Jiang)
  • Link: Are Performance-Optimization Benchmarks Reliably Measuring Coding Agents? — arXiv
  • TL;DR: If you're picking a coding agent based on published "makes code faster" benchmark scores (GSO, SWE-Perf, SWE-fficiency), be skeptical of the numbers — when researchers re-ran the benchmarks' own official correct-answer patches on different cloud machines, most failed to reproduce as valid on at least one machine type, meaning a good chunk of what looks like measured optimization skill is really machine-to-machine noise in how the benchmark is scored.
  • What to do: Don't rank coding agents by a single reported score on these performance-optimization benchmarks; if you build or rely on one yourself, re-run the reference solutions on your own target hardware before trusting the pass/fail bar.
  • Why trust it: Researchers replayed the official reference patches for 740 tasks across 4 Google Cloud machine types; the patches only reproduced as valid on every machine for 39 of 102 GSO tasks, 11 of 140 SWE-Perf tasks, and 411 of 498 SWE-fficiency tasks.
  • Skeptic check: This tests specific Google Cloud machine types — if benchmark maintainers use a more controlled or consistent environment than the ones tested here, real-world score noise could be lower than this suggests.

Long search sessions make models give up

  • Source: arXiv (Xia, Wang, Huang, Liu)
  • Link: Diagnosing and Mitigating Context Rot in Long-horizon Search — arXiv
  • TL;DR: In long research/search-agent sessions, models don't just get confused as context piles up — they increasingly give up or hedge with non-answers, and it gets worse the longer the session runs; the researchers tested several context-management tactics (pruning, summarization-style approaches, and a "rot-aware filtering" method) and found some genuinely reduce the give-up behavior while others just add cost without helping.
  • What to do: If you run long agentic search or research sessions, don't assume more accumulated context is free — build in active pruning or rot-aware filtering of old context rather than letting it grow unchecked, especially in sessions many tool-call rounds deep.
  • Why trust it: Tested across four flagship open-source models and three long-horizon search benchmarks, with controlled experiments isolating the effect of accumulated context length and seven different context-management methods compared head to head.
  • Skeptic check: Tested only on open-source models — it's unconfirmed whether frontier closed models show the same give-up pattern or benefit from the same mitigations, and exact per-method numbers couldn't be independently verified this run.

Fancy semantic chunking doesn't beat simple splits

  • Source: arXiv (Kreileder, Reisinger, Fischer)
  • Link: Evaluating Chunking Strategies for Retrieval-Augmented Generation on Academic Texts — arXiv
  • TL;DR: For RAG over long structured documents like academic papers or theses, fancier cluster-based semantic chunking did not beat plain fixed-size or recursive chunking on retrieval or answer quality in this test — and the popular RAGAs "faithfulness" score turned out to be unreliable in the same setup, so a good faithfulness number shouldn't be trusted without a manual check.
  • What to do: Don't reach for semantic or cluster-based chunking by default on long structured documents — start with simple fixed-size or recursive chunking, and manually spot-check a sample of RAGAs faithfulness scores rather than trusting the metric alone.
  • Why trust it: The researchers compared the three chunking strategies on long structured academic texts and scored results with the RAGAs framework, though the exact question count and corpus size weren't recoverable from search snippets this run.
  • Skeptic check: Results are specific to long, heavily structured academic documents — they may not transfer to short technical docs, code, or chat logs, and a single embedding/retriever choice could be confounding the chunking comparison itself.
