Eleven harness components determine whether coding agents ship reliable code

  • Source: Huang et al., arXiv:2605.13357, submitted May 13, 2026
  • Link: arXiv:2605.13357 — AI Harness Engineering: A Runtime Substrate for Foundation-Model Software Agents
  • TL;DR: When coding agents underperform, the gap is almost always in the harness — the infrastructure between model and codebase — not in the model itself. Researchers analyzed two production coding-agent systems (Claude Code and OpenHands) and found both must handle eleven distinct responsibilities: task specification, context selection, tool access, project memory, task state tracking, observability, failure attribution, verification, permissions, entropy auditing, and intervention recording. Missing any one is a reliability hole independent of which model you plug in.
  • What to do: Audit your agent harness against the eleven components; for each one, ask whether your harness handles it explicitly — any gap is a reliability fix you can make without swapping models.
  • Why trust it: Analysis of two deployed production coding-agent codebases (Claude Code TypeScript source and OpenHands), cross-referenced to derive the shared responsibility set; authors also propose a four-level ladder (H0–H3) grading how much runtime support is exposed to the agent.
  • Skeptic check: The eleven components were derived from two systems that share significant design philosophy; a harness built on radically different assumptions might partition responsibilities differently or identify additional components.

Agent benchmark scores overstate success when outcome checks are shallow

  • Source: Gao & Zhou, arXiv:2605.10448, submitted May 11, 2026
  • Link: arXiv:2605.10448 — Can Agent Benchmarks Support Their Scores? Evidence-Supported Bounds for Interactive-Agent Evaluation
  • TL;DR: Many agent benchmark tasks count a run as passed when a surface signal fires (the Save button was clicked, the command exited 0) without verifying whether the intended state actually changed. A meaningful fraction of "passed" runs on five major public benchmarks are unverifiable by the evidence the benchmark actually stores — meaning reported scores are partly fiction.
  • What to do: In your own agent evals, write outcome checks that verify actual state — database contents, file contents, API return values, or real side effects — not just surface signals like UI state or command exit codes.
  • Why trust it: Outcome evidence layer applied to five established public benchmarks (ANDROIDWORLD, AGENTDOJO, APPWORLD, tau-bench retail, and MINIWOB); each completed run assigned one of three labels (Evidence Pass, Evidence Fail, Unknown) based on what stored artifacts the benchmark actually captures.
  • Skeptic check: The paper diagnoses the problem and classifies existing checks; it does not supply correct replacement checks for every benchmark task — you still have to design the right verifications for your specific use case.

Per-span trace annotation localizes agent failures far better than outcome-only checks

  • Source: Madvil et al., arXiv:2605.14865, submitted May 14, 2026
  • Link: arXiv:2605.14865 — Holistic Evaluation and Failure Diagnosis of AI Agents
  • TL;DR: Knowing that an agent task failed tells you almost nothing about where in the trace the failure actually happened. Pairing a top-down task-level verdict with bottom-up per-span verdicts — scoring each tool call, reasoning step, and output independently — pinpoints the exact failing step and produces a rationale for each verdict. This scales to traces of arbitrary length because each span is assessed independently.
  • What to do: When debugging agent failures, annotate the trace span-by-span (each tool call, each reasoning block, each output) with an independent pass/fail verdict and a one-line reason before concluding anything about the overall failure — this localization step is what determines what to actually fix.
  • Why trust it: Evaluated on the TRAIL benchmark against GAIA and SWE-Bench; relative gains over prior baselines of up to 38% on category F1, up to 3.5× on localization accuracy, and up to 12.5× on joint localization accuracy.
  • Skeptic check: TRAIL is a structured benchmark purpose-built for this type of evaluation; whether the span-level gains hold for messier, longer traces produced by production agents on open-ended tasks is not shown.

How you compile skill context matters as much as which skill you retrieve

  • Source: Meng et al., arXiv:2605.10114, submitted May 11, 2026
  • Link: arXiv:2605.10114 — SkillRAE: Agent Skill-Based Context Compilation for Retrieval-Augmented Execution
  • TL;DR: When an agent retrieves a relevant skill from a library, most systems inject the full skill document into context. This paper shows that compiling the retrieved evidence — selecting only the most relevant sub-sections and compacting them before injection — produces substantially better task completion than injecting whole skill documents. The gain comes from the compilation step, not just from retrieval quality.
  • What to do: When writing skill files for your agent, front-load the critical execution steps and keep them tight; strip preamble, documentation prose, and examples that add tokens without adding execution value — the paper shows that what a retrieved skill contains at the start, and how compactly it is written, is what agents act on.
  • Why trust it: Evaluated on two public benchmarks; 11.7% improvement over prior state-of-the-art on SkillsBench, with ablations confirming that context compilation (not retrieval alone) drives the gain.
  • Skeptic check: SkillsBench is a controlled benchmark; whether the same skill-file structure choices matter equally in human-authored Claude Code skill files run against real, varied codebases is not directly tested.
