Claude Code now auto-loads plugins dropped into .claude/skills

  • Source: Anthropic — Claude Code changelog, v2.1.157, May 29, 2026
  • Link: Claude Code releases — github.com/anthropics/claude-code
  • TL;DR: Any plugin placed in a project's .claude/skills/ directory is now detected and loaded automatically when Claude Code starts — no marketplace install step needed. A new claude plugin init <name> command scaffolds the required folder structure. Autocomplete for /plugin subcommands and installed plugin names also ships in this release.
  • What to do: Move any local skill or plugin you've been manually registering into .claude/skills/ — it will be picked up on next launch with no other configuration. Use claude plugin init <name> to start new plugins from the correct template rather than copying by hand.
  • Why trust it: Documented in the official Claude Code v2.1.157 changelog entry, released May 29, 2026; deterministic tooling change with no benchmarks involved.
  • Skeptic check: Auto-loading scans the entire .claude/skills/ tree at startup; a malformed or untrusted plugin dropped there will be attempted — audit the directory before adding community-sourced plugins.

Claude Code dispatched subagent sessions now respect the agent field in settings.json

  • Source: Anthropic — Claude Code changelog, v2.1.157, May 29, 2026
  • Link: Claude Code releases — github.com/anthropics/claude-code
  • TL;DR: When Claude Code dispatches a subagent session (e.g. a Plan, Explore, or Task subagent), it now reads the agent field from settings.json and routes that session to the named agent profile. You can override per launch with --agent <name>. Previously, the field was parsed but not consistently applied to dispatched sessions, so subagents silently used defaults regardless of what you had set.
  • What to do: Add "agent": "<profile-name>" to your .claude/settings.json to pin which agent profile handles dispatched work; use --agent at the command line to override for individual sessions without touching the config file.
  • Why trust it: Official v2.1.157 changelog; deterministic behavior change that can be verified by inspecting which system prompt the dispatched session receives.
  • Skeptic check: Different agent profiles carry different tool access and system prompt composition — changing the routed agent for subagents affects what tools are available inside those sessions; test before applying to production harness configs.

Claude Code auto mode is now available on Bedrock, Vertex, and Foundry

  • Source: Anthropic — Claude Code changelog, v2.1.158, May 30, 2026
  • Link: Claude Code releases — github.com/anthropics/claude-code
  • TL;DR: Auto mode — where Claude picks the most cost-effective model tier on a per-turn basis inside long agentic tasks — is now available for Opus 4.7 and Opus 4.8 on Amazon Bedrock, Google Vertex AI, and Microsoft Foundry. Opt in by setting CLAUDE_CODE_ENABLE_AUTO_MODE=1 in your environment. Previously auto mode was only accessible on the direct Anthropic API.
  • What to do: Set CLAUDE_CODE_ENABLE_AUTO_MODE=1 in your enterprise deployment to try auto mode; it can reduce token spend on simple turns within long-running agentic tasks by routing those turns to a cheaper model tier automatically.
  • Why trust it: Official v2.1.158 changelog entry, released May 30, 2026; the opt-in environment variable is the only required change.
  • Skeptic check: Auto mode delegates model-tier selection to Claude, removing your ability to guarantee which model handles each turn — if your compliance posture or billing model requires a specific model per call, keep it off.

Windsurf MCP tool permission grants now survive session restarts

  • Source: Windsurf changelog — Devin Local agent v2026.5.26, ~May 29, 2026
  • Link: Windsurf changelog — windsurf.com
  • TL;DR: When Windsurf's Devin Local agent prompts for MCP tool permission, you now get two new server-level options alongside the existing per-tool prompt: "approve all tools on this server for the current session" or "approve permanently." The permanent grant survives session restarts. Previously all grants reset at session end, requiring re-confirmation on every new session for every MCP server.
  • What to do: For MCP servers you own or fully trust (internal tools, personal servers), use the permanent grant option to stop being interrupted mid-task; for third-party or external MCP servers, use per-session grants to keep an audit trail of what each session accessed.
  • Why trust it: Documented in Windsurf's public changelog as part of the Devin Local v2026.5.26 update; changelog page returned 403 so confirmed via search-aggregator summaries. Exact release date within the window is approximate.
  • Skeptic check: Permanent grants survive MCP server code updates that might introduce new tools — review your permanent grants whenever you pull a new version of a server you've already granted permanently.
