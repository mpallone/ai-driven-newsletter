Mark read-only MCP tools with readOnlyHint to run them in parallel in Codex CLI

  • Source: OpenAI Codex CLI changelog — v0.134.0, May 26, 2026
  • Link: openai/codex v0.134.0 — GitHub Releases
  • TL;DR: The Codex CLI now runs MCP tools concurrently when the tool's schema declares readOnlyHint: true. Previously all tool calls ran sequentially regardless of whether they could safely overlap. The same release also adds searchable local conversation history (case-insensitive, with previews) and passes full conversation history into extension hooks, so hooks can now react to prior context rather than just the current turn.
  • What to do: Audit your MCP server tool definitions and add readOnlyHint: true to any tool that only reads data (file reads, search, database lookups, API GETs); those tools will now run in parallel under Codex CLI, cutting round-trip time when the model calls several in one turn. If you write Codex extension hooks, update them to use the new conversation-history field in hook inputs.
  • Why trust it: Change is documented in the official Codex v0.134.0 release notes published May 26, 2026 at 16:46 UTC on GitHub; the behavior is a deterministic code change, not a benchmark claim.
  • Skeptic check: readOnlyHint parallelism is currently Codex CLI-specific; Claude Code, Cursor, and other MCP clients may not yet honor the hint for concurrency, so the benefit is narrowly scoped to Codex CLI users today.

Add CWE mitigation steps to code-gen prompts to cut security issues by 57–95%

  • Source: Mohammad Kharma et al. — arXiv cs.SE, submitted ~May 22, 2026
  • Link: Enhancing Reliability in LLM-Based Secure Code Generation — arxiv.org
  • TL;DR: When prompting LLMs to write code, adding a structured chain-of-thought step that names the relevant CWEs (Common Weakness Enumeration) for the task and asks the model to reason through mitigations before writing the code cuts the count of security issues in the output by 57.6% in the primary test set and 94.5% in the validation set. Plain zero-shot and standard chain-of-thought prompting do not reliably improve security—and in C they can make it worse.
  • What to do: For any task that generates security-sensitive code, add a section to your prompt that (1) names the CWE categories relevant to the task (e.g., CWE-89 for SQL, CWE-79 for web output, CWE-120 for C buffer operations) and (2) asks the model to reason through the mitigation for each before writing the implementation. Do not rely on a bare chain-of-thought or a generic "write secure code" instruction—neither reliably helps.
  • Why trust it: 200-task primary dataset evaluated against three LLMs (GPT-5, Claude 4.5, Gemini 2.5) and three languages (C, Java, Python), with an external validation set (LLMSecEval); vulnerability counts verified via static analysis with expert review.
  • Skeptic check: The 94.5% figure is from the smaller LLMSecEval validation set; the 57.6% primary-set figure is more representative. LLMSecEval tasks are constrained and may not cover the full complexity of production code; gains on benchmark prompts may be smaller in real workflows.
