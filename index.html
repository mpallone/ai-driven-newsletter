Claude Code /goal replaces turn-by-turn task supervision

  • Source: Anthropic, Claude Code v2.1.139, May 11, 2026
  • Link: Claude Code v2.1.139 — GitHub releases
  • TL;DR: The new /goal command takes a plain-English completion condition ("all tests pass", "the PR description is ready") and keeps Claude running turn after turn until a small fast model checks the condition and confirms it is true — you don't supervise each turn, you come back when it's done. The same release adds agent view (claude agents): a single dashboard listing every session with its state (running, waiting for your input, done), so you can manage several background tasks without juggling terminal tabs. Also fixed: Bedrock and Vertex users were getting 400 errors when ENABLE_PROMPT_CACHING_1H was set; that is now resolved.
  • What to do: Update to v2.1.139 (npm update -g @anthropic-ai/claude-code), then try /goal all tests pass on a well-scoped task to see the autonomous loop in action; run claude agents if you regularly juggle more than two parallel sessions.
  • Why trust it: Official Anthropic release; version number (v2.1.139, May 11) confirmed from the Claude Code GitHub releases page and multiple third-party summaries citing the same changelog; feature mechanics described consistently across Anthropic docs (code.claude.com/docs/en/goal) and the official Anthropic blog post on agent view.
  • Skeptic check: The fast model that checks the condition after each turn adds latency and token cost per loop iteration; for simple tasks this overhead may outweigh the convenience gain — benchmark on your own workload before using it as the default.

Bugbot high effort finds 36% more bugs per run

  • Source: Cursor, changelog entry May 11, 2026
  • Link: Cursor changelog — May 11, 2026
  • TL;DR: Cursor's Bugbot PR reviewer now ships with three configurable effort levels: Default (0.7 bugs found per run on average, fast), High (0.95 bugs per run, slower and more expensive), and Custom (you write a natural-language rule — "use high effort for PRs touching payments code" — and Bugbot decides per-PR). The jump from Default to High is roughly 36% more bugs caught per run. Alongside this, Bugbot drops its flat $40/seat/month fee and moves to usage-based billing for Teams and Individual plans; you only pay for reviews that actually run.
  • What to do: Use Default effort as your baseline; switch to High or a Custom rule only for PRs in high-risk areas (auth, payments, data migrations) where catching one extra bug justifies the increased cost and wait time; check your Bugbot spend after the first billing cycle under usage-based pricing.
  • Why trust it: Cursor's own changelog with per-tier average bug counts (0.7 Default, 0.95 High) drawn from Bugbot's production run history; the 79% "resolved at merge" figure for Default effort adds a baseline quality signal. Cursor's own data — no independent replication.
  • Skeptic check: "Bugs found per run" averages obscure variance — for a specific repo or team, high effort may find zero extra bugs or many more; calibrate on your own PR history before locking in a blanket high-effort policy.

Make any LLM prompt script directly executable

  • Source: Simon Willison, simonwillison.net, May 11, 2026
  • Link: TIL: Using LLM in the shebang line of a script — Simon Willison
  • TL;DR: Simon Willison's LLM CLI tool can live in a shebang line, making a plain-text file a first-class executable. Minimum working form: #!/usr/bin/env -S llm -f Generate an SVG of a pelican riding a bicycle. The -S flag is essential — without it, env treats everything after the command name as one string instead of splitting into separate arguments. To add tool calls, append -T tool_name; to bundle a full prompt with custom Python tool functions, point the shebang at a YAML template file instead of an inline -f string.
  • What to do: If you use the LLM CLI tool, turn your frequently-reused prompts into chmod +x scripts in your ~/bin directory — they become self-documenting, composable with pipes, and callable from shell aliases or other scripts.
  • Why trust it: Simon Willison is the author and maintainer of the LLM CLI tool; the technique is a working code snippet from his own TIL blog, confirmed executable. The -S flag behavior in env is a documented POSIX extension present in GNU coreutils and macOS.
  • Skeptic check: Works only if the LLM CLI tool is installed in the environment where the script runs; breaks silently in Docker images or CI environments that do not have it, so check portability before relying on shebang scripts in shared pipelines.

Claude Platform on AWS reaches general availability

  • Source: Anthropic / AWS, May 11, 2026
  • Link: Introducing the Claude Platform on AWS — Anthropic blog
  • TL;DR: AWS is now the first cloud provider hosting a full Anthropic-native Claude Platform — not just model access via Amazon Bedrock, but the complete API surface: Messages, Files, Batch, Managed Agents, Agent Skills, and code execution, authenticated through AWS IAM and billed through your existing AWS account. Opus 4.7, Sonnet 4.6, and Haiku 4.5 are available at launch; new models will ship there as they release. No separate Anthropic account is required.
  • What to do: If your stack already runs on AWS, evaluate switching to the Claude Platform on AWS endpoint to consolidate billing and access Managed Agents and Agent Skills without maintaining a separate Anthropic API key; review IAM permission requirements and check regional availability against your data-residency constraints before migrating production traffic.
  • Why trust it: Joint announcement from Anthropic and AWS; GA date of May 11, 2026 confirmed on the official AWS "What's New" page and the Anthropic blog, with the announcement consistent across multiple independent tech news sources.
  • Skeptic check: Anthropic noted this is for teams without specific regional data-residency requirements — if your workload is residency-constrained, verify the available Claude Platform on AWS regions before migrating.
