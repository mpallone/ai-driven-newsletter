Cursor 3.8 adds /automate, GitHub/Slack triggers, and computer use to automations

  • Source: Cursor changelog (June 18, 2026)
  • Link: Cursor changelog — Improvements to Cursor Automations
  • TL;DR: The new /automate slash command turns a plain-English description into a fully configured automation — triggers, instructions, and tools set up for you, without hand-editing a config. New GitHub event triggers (issue comment, PR review comment, PR review submitted, review thread updated) join the existing push/PR triggers. A new Slack emoji-reaction trigger fires an automation directly from any Slack message. Computer use is now available inside automations, enabling agents to interact with GUIs as part of automated workflows.
  • What to do: Use /automate in your current session instead of manually building automation configs — describe what you want and Cursor configures it. Wire up the new GitHub PR review triggers if you want code-review comments to kick off agent work automatically.
  • Why trust it: Cursor official changelog, June 18 2026, at cursor.com/changelog/06-18-26; consistent with Cursor's previously-announced Automations platform.
  • Skeptic check: Computer use in automations may require a Teams or Business plan; Standard seats should verify access before building workflows that depend on it.

Claude's Team and Enterprise plans now push MCP connector access to users automatically

  • Source: Anthropic blog + MCP Protocol blog (June 18, 2026)
  • Link: Enterprise-Managed Authorization — Anthropic blog
  • TL;DR: Admins can now authorize MCP connectors once through their identity provider (Okta first), and users get zero-touch access on first login — no more asking every developer to individually authorize each connector. The underlying mechanism is XAA (Cross App Access), an OAuth 2.0 extension that is now a formal part of the MCP spec. Asana, Atlassian, Canva, Figma, Granola, Linear, and Supabase support it at launch; Slack is coming soon. In beta for Team and Enterprise plans.
  • What to do: If your org runs Claude on Team or Enterprise, connect your Okta account and push MCP connector access org-wide now — this eliminates the per-developer authorization friction that has blocked MCP adoption at scale.
  • Why trust it: Anthropic primary blog post (June 18 2026); confirmed by the MCP Protocol official blog post at blog.modelcontextprotocol.io and an Okta press release naming Okta as the first identity provider.
  • Skeptic check: Only Okta is supported at launch; orgs on other identity providers (Entra ID, Google Workspace, etc.) must wait for additional IDP support before this is usable.

Claude Code 2.1.183 blocks destructive git and IaC commands it didn't create

  • Source: Anthropic Claude Code changelog (June 19, 2026)
  • Link: Claude Code changelog — Anthropic
  • TL;DR: In auto mode, Claude Code now refuses to run git reset --hard, git checkout -- ., git clean -fd, or git stash drop unless you explicitly asked it to discard local work. git commit --amend is blocked if the commit being amended wasn't made by the agent in this session. terraform destroy, pulumi destroy, and cdk destroy are blocked unless you specifically named that stack for destruction. Also in this release: a warning when your configured model is deprecated or has been silently auto-upgraded; an attribution.sessionUrl setting to stop Claude Code from appending a claude.ai session URL to commit messages and PR descriptions; and /config --help to list all valid shorthand keys.
  • What to do: Run claude update; set attribution.sessionUrl to false in your project config for clean git history. Check agent frontmatter files for deprecated model names — you'll now get a visible warning on stderr rather than silent substitution.
  • Why trust it: Anthropic official Claude Code changelog, June 19 2026; directly addresses GitHub issues #34327 (agent running git reset --hard on session startup and destroying uncommitted work) and #17190.
  • Skeptic check: The guards trigger on commands the agent issues on its own; if you explicitly ask it to reset or destroy, it will still comply — so protection only applies to uninstructed destructive actions.

Google DeepMind publishes a 15-control layered framework for safe agent deployment

  • Source: Google DeepMind blog + AI Control Roadmap PDF (June 18, 2026)
  • Link: Securing internal systems against increasingly capable AI — Google DeepMind
  • TL;DR: Google DeepMind published its internal AI Control Roadmap — the framework they actually use to deploy AI agents inside Google. The threat model has three buckets: loss of control (rogue internal deployments), sabotage of safety research, and direct harm (data deletion or theft). The response is 15 controls layered across two tiers: detection (ranging from chain-of-thought log review up to scrutiny of models whose reasoning is opaque) and response (ranging from async human review down to real-time blocking). The key architectural pattern is a trusted supervisor agent that continuously monitors the primary agent's reasoning and actions with override capability — described as a driving instructor with dual controls.
  • What to do: When designing agent harnesses that touch sensitive internal systems, add two explicit tiers to your safety architecture: what you will monitor (agent reasoning traces, action logs) and what triggers intervention (threshold for human review vs. real-time block). The dual-control pattern — a supervisor agent that can halt the primary agent — is implementable today in any multi-agent setup.
  • Why trust it: Primary source blog post by Rohin Shah at Google DeepMind (June 18 2026), with an accompanying public PDF; independently covered by Axios on the same date.
  • Skeptic check: The roadmap describes Google's threat model for large-scale internal deployments; many of the 15 controls assume dedicated supervisory models and real-time action interceptors that most smaller teams won't have.
